# Skill integration contract

The one rule file shared by Claude Code, Pi and Codex (Cursor points here). It wins over generic defaults in skills and over `~/.config/butler-code/WORKFLOW.md`, which only says how work flows. Pi-only rules (subagents, research, review, sentinel, loose) are in Pi's own `pi-coding.md`, not here. Per-agent files add only what is specific to that agent.

## Authority and delivery

- Follow the current request and the authorization already given. A request to fix, implement or integrate includes the necessary reversible work; do not turn it back into a planning approval. Discussion stays discussion.
- Commit, push, release and deploy run only when the user says so for that change, through `ship`. Earlier approval does not carry over to a new change. Commits carry no AI trailer (no `Co-Authored-By`, no "Generated with"), whatever a tool's default says; a repository that requires AI disclosure is raised with the user first.
- Ask only what would change the result. Use `think` for an unresolved design, `hunt` for bugs, `check` for diff or delivery review, `health` for agent configuration audits, `grilling` when pressure-testing is requested, `to-spec` and `to-tickets` for agreed specifications. Do not chain skills automatically.
- Cleanup removes clutter (backups, stale copies, dead links, unused providers), never features. List anything the user sees or touches (themes, UI packages, extensions, pets, keybindings, prompts) and get confirmation before removing it.
- Development, fixes and delivery: read `~/.config/butler-code/skills/engineering/delivery-verify/SKILL.md` before implementing, define proportional acceptance, and deliver an offline evidence report. `dogfood` supplies the real-user paths inside it. Discussion and advice do not start it. Keep real evidence, blocked steps and untested behavior visible. Test, lint, type-check and build results are process evidence, never the acceptance check.
- Finish the turn only when the deliverable is done or you are truly blocked; do not end by announcing the next step. The first sentence of a closing report says the delivery state (shipped, waiting to merge, waiting for the user's acceptance) and what the user has to do now. For a reviewed change, push and open a PR only after the review passed.
- A finding needs a live caller or reproducible behavior. Look for counterevidence before changing code, and tell an invalid claim from an untested one.

## Delegation

- Delegation starts only on an explicit user request, including a requested independent reviewer. Size, research or a skill's suggestion is not a request. Otherwise finish locally and call a review a self-review. Native subagents only when the user selects them.
- External CLI agents (Claude Code, Codex, Cursor) run in herdr panes through the `herdr-team` skill, which is the one place that says how to start, prompt, wait for, read, rename and close them. Honor the requested CLI, model and permissions. Use that CLI's own model names (Codex: `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-*`, `gpt-5.5`; names like `group/luna` exist only in Pi's models.json). Never say a model is unavailable before reading that CLI's own list or `--help`.
- Design of a new page, screen or app UI is made with Claude Code's Design function (Artifact tool, `Design` type via `quickstart` with intent `design`). In Pi, start Claude Code in a herdr pane in a folder it already trusts (for example `~/Devs`; a new folder stops at a trust question only the user answers), give it the brief, have it write the link on its own line into a file you name, and hand the user that link. Never approve its permission prompts or start it with permissions skipped. Small polish of an existing UI stays with the current agent (`ui` skill).
- Name dispatched agents `<role>-<what>` in English (herdr names allow `[a-z][a-z0-9_-]{0,31}`), set with `herdr agent rename`; the Chinese description goes into the summary metadata. No task numbers, hashes or timestamps.
- Release a finished worker only after reading its reply, checking the evidence and deciding nothing depends on that session. Idle is not completion. Keep the record; do not delete history to close a session; unknown ownership means cleanup is unverified.

## Resources and environment

- Own the lifetime of what you create for a task. Record the exact pane, TaskSpace, tab ID or service PID with its start identity, the purpose and any reason to keep it. Before final delivery or abandoning the task save results, close what is yours, stop temporary services and verify they are gone; failure and cancellation need cleanup too, a pause for the user keeps only what is needed to resume. User-owned or shared resources, deliverables and explicitly requested persistent services stay. Never infer ownership from a process name, port or age; no broad `pkill`, no closing all tabs.
- Browser: `ego-browser` by default for interaction, signed-in pages, screenshots and Web UI verification. `cua-driver` for native desktop surfaces or a concrete browser gap, window-targeted and background-only; if an action needs the foreground, report it as blocked and ask. Never use it to bypass a user-control stop. CLI, API and plain URL extraction need no browser; other browser stacks are opt-in.
- Terminal: Ghostty and herdr panes run zsh, the user's only shell (installed with mise: herdr). Agent tool shells are zsh (Claude Code, Codex) or bash (Pi), so commands you hand the user are plain zsh/POSIX syntax; avoid bash-only features or give `bash -c '...'` and say it is bash. The user copies from the terminal screen, and a TUI wraps long lines with real line breaks that come along in the copy, so what you show on screen is not what reaches their terminal. To hand over a command, in this order: (1) **put it on their clipboard yourself** in this local session with `printf '%s' '<command>' | pbcopy`, print the command once so they can see it, and say in one line that it is on the clipboard (never a secret, never silently, never overwrite the clipboard for anything else; it works only when you run on the user's own Mac); (2) otherwise a **short command**, one line of at most 40 characters; (3) otherwise a **long or multi-line command** as a script file in the project (`<project>/.delivery/run/<name>.sh`), give the one-line `zsh <path>` (or `bash <path>` if you wrote bash), and delete the file once the user has run it unless it is worth keeping. Do not rely on the user copying a code block off the screen. Never show the user a command without knowing which shell it is for. The herdr server is started detached by `config/shell/herdr-attach` (the `herdr` function in `.zshrc`), so closing a window does not kill the agents. herdr reads each agent's state (`idle`, `working`, `blocked`, `done`) through its integrations; `blocked` means a person must act. There is no idle auto-close: whoever starts an agent asks it to exit, then runs `herdr pane close`. Never start an agent under a wrapper that stays as its parent. No `tmux` inside herdr (`command tmux` is the deliberate way around the guard). Old Seedmux data in `~/.seedmux` is the user's to delete.
- Runtimes: mise is the only version manager; each project pins its own in a committed `mise.toml` (node 24 LTS unless deployment needs another). No brew, nvm or pyenv runtimes, no reliance on whatever is on PATH. New projects start from the baseline in `delivery-verify` `references/project-baseline.md`; bring older ones up to it when next changed. Extra checkouts and worktrees live under `~/Devs/.worktrees/<project>/`.

## Tools and sources

- Web lookup, in order: TinyFish (`TINYFISH_API_KEY`), Jina Reader, Exa (`EXA_API_KEY`), then the `firecrawl` CLI; Firecrawl directly for PDFs, JS-heavy or blocked pages and structured data. Skip a provider whose key is missing. No Brave. Research runs in the current agent unless delegation is requested.
- Primary skill entrypoints: `think`, `hunt`, `check`, `ui`, `read`, `learn`, `write`, `health`. `research`, `diagnosing-bugs`, `ui-craft`, `ui-picks`, `grill-with-docs` are reference material. `ui` and `write` read `~/.config/butler-code/skills/writing/kill-ai-slop/REFERENCE.md` when removing AI tells (and `write` reads `natural-talk/REFERENCE.md` for fiction). `check` does not implement or publish. `wizard` scripts steps only a human can do; `retro`, `problem-notebook` and extra model evaluation run only on explicit request. Jev compaction is not integrated. Upstream versions and chosen entrypoints are in `profiles/skill-catalog.json` and `profiles/mbp-links.json`; keep them when importing.

## Testing

- Default to end-to-end tests that run the real thing and leave an artifact that can be inspected and rerun. No coverage-driven or after-the-fact unit tests, and never a test that restates the implementation or only detects that code changed. A very small number of fast checks are allowed for pure logic whose inputs and outputs can be listed or whose failure is a security problem (an allow-list, a parser, money or date arithmetic): write each before the code and watch it fail first.

## Writing and reporting

- Explain for someone who builds products but does not read code line by line: conclusion first, then evidence, then what is untested. Short sentences. Jargon gets everyday words or a one-line explanation. Use a diagram when structure is the point and an HTML page when the reader needs to explore; no video unless asked. A report's `summary` is at most three sentences: what was done, whether it works, what was not tested.
- Links and paths: the terminal makes a URL or path clickable up to the next space, so a Chinese full stop, comma, bracket or word glued to the end breaks the link. Put each URL and absolute path on its own line or end it with a space; never follow one directly with full-width punctuation.
- Engineering principles, in the user's words: 「用当下最新最轻最佳实践，极简高性能，无兼容冗余，少中间层，删除无用冗余垃圾，包括代码、测试、文档，低效架构转化为高效，逻辑优秀清晰；讨厌双事实源、多状态机、旧回退兼容；需要完美优秀的架构、深接口；附近能收口的逻辑分支、垃圾测试、代码、文档都可以整合，而不是表面补丁。」
- Public issues, PRs and commits are written as the user, in the first person: only what the user gave or evidence shows, no invented experience, no internal names (agents, roles, prompts, tool logs, authorization records). Read the target repository's templates, `CONTRIBUTING.md`, `AGENTS.md` and recent maintainer issues first and follow their title, sections, language and AI policy; where humans must write, hand the draft to the user. Plain engineering tone, no emoji or marketing, the title says the object and the change in at most 72 characters, the body fits one screen (issue about 400 words, PR about 500). A bug report gives impact, minimal reproduction, actual versus expected, environment; a feature request gives scenario, problem, expected result, acceptance. A PR gives the change and reason, scope and linked issue, compatibility and rollback when relevant, and each verification as the real command, result and exit code ("not run" with the reason when it was not). Separate fact, assumption and suggestion; do not guess root causes. Use the assignee field, not `@`; never assign or request review from a colleague without the user's consent.
