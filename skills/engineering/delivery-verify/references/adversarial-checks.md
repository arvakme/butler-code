# 维护者式复核：CI 全绿之后还要查什么

来源：yetone/magpie 的维护者在我们两个 PR（#360 Grok 生图生视频、#391 手机网页）上的复核记录。CI 当时都是绿的（go vet、三个系统的测试、竞态测试、无 GUI 构建），他仍然每次都找出新问题。他没有更聪明的 CI，是在 CI 之外做了下面这些事。交付前对每个验收项过一遍，不用全做，但每一条要有"做了/不适用，理由"。

## 查什么

1. **真实产品，真实数据。** 用沙盒 HOME 启动真正的程序，让它检测到真实存在的东西。测试夹具里 `agents: []`，Agent 行根本不会渲染，给那一行加 20px 内边距桌面对比照样通过，真问题就测不出来。先确认夹具真的让被测的东西出现在屏幕上。
2. **测试必须能变红。** 把本次改动撤掉再跑新测试，必须失败（他数过：撤掉后失败 9 项）；用修复前的提交跑新测试，之前报告的问题必须被测出来；故意把一个元素挪 2px，用量页要失败，不改要稳定通过。绿的测试没有变红过，就不算证据。
3. **和基线对比，不是自己对自己。** 截图对比的基准取自 `origin/main` 的文件（`git show`），像素差异设容差（单通道差大于 48 才算，超过 300 个像素才失败），并先用同一份代码对比自己，排除误报。
4. **矩阵，不是单点。** 引擎（Chromium 加 WebKit）× 视口（手机 360/390/430、平板 820、桌面 900/1280）× 语言（中、英）× 所有页面；还有明确的支持下限（Safari 15.0 不支持 `100dvh`，有专门的旧 WebKit 测试守着，加了回退值也不行）。
5. **老用户升级。** 用"上一个版本写出来的状态"做起点：已经装好的条目照旧版的样子放着，升级后新默认值会不会到达老用户（实际上同步命令说"每个 agent 都已有了"，什么也没改）；用户自己改过的值要保留。
6. **输入边界。** 解码后的 id 拼进 URL 前要校验：`%3F`、`%2F`、`..%2F`、`%23`、空格、`%2e%2e` 都要被拒绝，测试还要断言上游一个请求都没收到。
7. **开关语义。** 关掉"生图"，"生视频"也该关；一个开关的每个入口都要读它。
8. **客户端默认值。** 长操作最长 10 分钟，而客户端（Codex 的 MCP 工具）默认超时较短，agent 超时后重试会重复扣费：写长超时，或者先返回 id 再轮询。
9. **状态里缺的信息。** 视频 id 没记是哪个账号生成的，中途切换账号就查不到了。
10. **抖动归因。** 失败先在基线上复现；基线上也一样就写"main 上同样出现，与本次无关"，不要硬算在这次改动头上，也不要含糊带过。

## 他的流水线怎么设计（我们自己的项目可以照做）

- 改了界面的 PR 自动用 PR 构建出真实的应用，用 Playwright 驱动并截图、录屏（画上鼠标），贴在 PR 描述的固定位置。
- fork 来的 PR 用 `pull_request_target`，脚本取自 main；PR 的代码只在拿着低额度 key 的 record 作业里运行，有写权限的 publish 作业从不运行 PR 的代码。

## 用在我们的验收里

写验收项时多问自己五件事：这次用的是真数据吗？这个测试撤掉改动会红吗？和基线比过吗？矩阵里最容易坏的是哪几格？老用户升级之后会怎样？再看用户输入进了哪些拼接、开关有几个入口、长操作超过客户端默认超时吗。查出来的问题按 SKILL 第 4 节写进 `common-mistakes.md`，变成守卫。
