# Delivery verify

交付的是可检查的结果，不是“测试过了”的承诺。默认用于开发、修复、新项目和交付；纯聊天、研究或仅给建议不生成报告。普通小改缩小验证范围，不机械跑全量或调起浏览器。

沿用 `~/.config/butler-code/config/instructions/skill-integration.md` 的授权、工具与工程原则。委派只在用户明确要求时进行；外部 CLI 经 herdr（`herdr-team` skill）派发，其余 agent 经 Agora，原生 subagent 仅按用户明确选择使用。

## 0. 项目层

先运行 `share.py list --json` 看还有哪些项目和交付在并行（只是了解全局，不必逐个读）。再读项目的 `.agents/acceptance/PROJECT.md` 与 `common-mistakes.md`：怎么启动、端口、账号、入口听项目的，不自己猜。没有就按 [项目适配层](references/project-adapter.md) 在本轮建立。新项目或缺 `mise.toml`、`AGENTS.md` 的老项目，先按 [项目基线](references/project-baseline.md) 补齐，再做需求。

## 1. 写验收项

从用户原话出发，不从分支名或改动的代码层出发。每个验收项是用户会点“接受/打回”的一个效果：入口、动作、预期、必需证据；有多个独立用户任务时按任务分组。执行前确定哪些是必验项，失败后不能改成可选。

- **硬规则**：单测、类型检查、lint、构建、CI 只进 `checks`，永远不是验收项。
- **选界面**：按用户能看到的结果选最省的证明方式。只有无界面结果时才只用 CLI（保存输入、原始退出码、输出或副作用）；Web 用 Ego；原生窗口或浏览器能力缺口用 Cua 后台定向操作。后端改动若结果体现在界面上，仍要在界面上验。
- **覆盖**：对照 [常见错误清单](references/common-mistakes.md) 补上相关的边界状态（错误态、窄屏、主题、键盘、共享组件的每个入口），不只测最顺的路径。
- **CI 全绿之后**：对照 [维护者式复核](references/adversarial-checks.md)（真实数据、测试能变红、基线对比、矩阵、老用户升级、输入边界、开关与超时），每条写“做了”或“不适用及理由”。

先读 [判断检查表](references/judgment.md)。产物放在项目自己的隐藏目录 `<项目根>/.delivery/<任务>/round-01/`（项目另有约定就沿用它）；git 项目把 `.delivery/` 写进 `.git/info/exclude`（本地忽略，不改仓库里的 `.gitignore`）。不要放进 butler-code：它只放 skills、MCP 和协作规则。读 [报告格式](references/report-format.md)，从 [数据示例](assets/result.example.json) 建立 `result.json`，这是本轮唯一报告数据源；开始时状态 pending。

**独立审查**：只有用户明确要求另一位 Agent 审查时才派发，通过 herdr（`herdr-team` skill）；跨文件、数据写入或 skill 建议本身不触发派发。其余由当前 agent 对照用户要求和证据自审并如实标注。用户要求的审查在其指定范围和成本内进行。

## 2. 实现并取得证据

按项目入口从最窄受影响检查开始，记录原始命令、裸退出码和日志；按依赖风险扩大。审阅实际 diff 及调用路径，区分代码审查、自动测试、用户行为三种证据。

写、改或清理测试时读 [测试参考](references/testing.md)：每条测试过价值门；行为变更先写测试并亲眼见红，记录测试文件指纹锁住，实现后核锁，指纹不一致即停下说明。本轮开始时项目已有的检查若本来就是红的，先报告，不当作本次改动的结果。

有可执行行为时读取 `~/.config/butler-code/skills/engineering/dogfood/SKILL.md`，按验收项操作真实入口。遇到用户接管、权限、需要前台焦点或弹窗确认时停止该路径，标记 blocked，不切换工具绕过。文档等无运行行为的任务说明不适用原因，不造证据。

跨页面、多步交互或动态效果需要录像时读 [交互录像](references/recording.md)：复用 Ego 的真实画面帧，记录轨迹、点击圈、字幕及实际结果；静态改动沿用截图。

边执行边保存最少但足够的过程与最终效果。每份证据注明运行版本、采集时间和工具；实际查看后才标 inspected。测试日志不能证明视觉效果，截图不能证明持久化或后台副作用。去除凭据及无关私人内容；默认不上传、不调用额外评估模型。

修复授权内的问题，重走原失败路径及相关回归。外部阻塞时完成独立部分并保留缺口。中断也保存实际结果，不补写从未发生的步骤。

## 3. 结论与离线报告

标 `passed` 前再对照一次常见错误清单与判断检查表。记录自审或实际 worker 回执，不把当前 agent 的多遍检查说成独立审查。记录本轮创建的资源句柄并收尾验证；共享资源保持原样，有意保留的写明理由；无法确认清理时 `cleanup.complete` 为 false。

执行 `scripts/report.py /absolute/path/to/result.json`（只需 Python；界面源码在 `ui/`，改界面按报告格式里的构建说明）。生成成功仅表示报告有效，**不代表验收通过**；失败、阻塞也要生成报告。按 [交付看板](references/sharing.md) 把本轮目录登记到固定端口的看板（反馈绑定当前 agent 自己的 herdr pane），在 Ego 里核对页面、附件和一次反馈回执，把这份报告的 Tailscale HTTPS 地址给用户（看板是给 agent 的，不默认发给用户）。简述结论、未测范围和保留资源。localhost、file://、裸 HTTP 和本地路径不能作为用户交付链接。“验证通过”仍是“待用户验收”，不自动提交、推送或发布。

## 4. 用户逐项打回

页面按钮直接提交反馈到绑定会话，完整正文与回执保存在本轮 `feedback-receipts/`；未知投递不自动重发。从反馈定位稳定验收项 ID（回执里 `accepted` 是用户已接受的项，`ignored` 是用户说不用处理的项，不要为它们返工；`rejected` 带原因标签、图上和视频里的位置意见、是否存成教训；每轮可写 `message` 说明改了什么、请看哪里，开工前顺手读一眼上一轮的 `reactions.json`），建下一轮目录并用 `previous_report` 链接上一轮，记录 feedback。用户已接受的项保持关闭不重跑；只重做打回项和受改动影响的项，复用证据时保留原采集时间与版本并说明理由。需求变化或新发现补为新验收项，不删旧失败，被替代的项在 observation 写明由哪一项接替。

每次打回，把原因写成一条可检查的规则追加到项目 `.agents/acceptance/common-mistakes.md`，下一轮交付前先对照；能写成命令加预期结果的，同时补成守卫或测试，让它能自动重跑。旧轮报告和证据不覆盖。

## 5. 上线后

有线上服务的项目，发布不在“提交”时结束：按 `PROJECT.md` §2 在部署后立刻跑生产冒烟与回读，并在 24 小时后再跑一次回读。回读验证数据仍在更新，而不只是页面可访问。任一回读失败，发布视为未完成，回到第 2 步排查；把原因记入 `common-mistakes.md`。定时回读由常驻设备执行，失败时通知用户。
