# PR 正文

来源：mattpocock/skills 的 `pr`（其中“Summary 用什么图”一节来自 Dex Horthy 的 `show-me`，见 https://github.com/humanlayer/humanlayer），按本机规矩改写后并进 `ship`。

## 先看规矩

- 目标仓库有 PR 模板、`CONTRIBUTING.md` 或维护者惯用的格式，先按它写；没有这些时才用下面的模板。
- 正文以用户本人的口吻，不加 AI 署名或“Generated with”之类的标记，不写 agent 名称、提示词、工具日志；一屏之内，约 500 字以内。
- 验证写真实运行过的命令、结果和退出码；没运行就写“未运行”和原因；失败项列出来；不把推测写成已确认的根因。
- 用项目自己的领域词汇（`CONTEXT.md` 或 `GLOSSARY.md`），不写没解释过的行话。

## 模板

```markdown
## Summary

<一张图、一段伪代码、一棵树或一段 diff：挑最小的、能把重点说清的>

## Evidence

- **Before：** <截图 / 输出 / 失败的测试>
  **After：** <截图 / 输出 / 通过的测试>

## Merge Danger

**Door：** <单向门 / 双向门>

<可选：说明>

**Blast Radius：** <一个词概括影响面>

<可选：合并后可能的连带影响>
```

开头不写寒暄，文字尽量短。

### Summary 用什么图

选最小的那一种，把图放在支持它的那句短文字旁边；只留回答当前问题所需的调用、文件、属性、状态和边界。可以用一种，也可以用几种，通常用不满，别淹没读者。

- 逻辑或算法：伪代码。
- 运行时控制流：调用树（`submitForm` 下缩进它调用的 `createSession`、`navigateToSession`）。
- 界面结构：组件树，带上要紧的状态和模块边界。
- 文件职责或大重构：浅层文件树，每个目录一行注释。
- 组件交互、控制流或数据流：Mermaid（`sequenceDiagram` 等）。
- 主要在说“改了什么”、周围结构本来就在：用 `diff`，并让 diff 的形状贴合主题（组件树的 diff、文件布局的 diff、调用树的 diff、状态流的 diff）。
- 大部分是新代码、省略上下文会看不出归属或顺序，或者读者需要一段能直接复制的目标形状：给完整代码块。

### Evidence

要有能证明改动有效的具体证据，写出前后对比。

- 截图是最好的证据，前提是环境能截、改动是看得见的。
- 其次是执行证据：测试结果、控制台输出；用伪代码写出现在失败又变成通过的那条具体测试。
- 界面改动按本机规矩附能看出差异的截图或录屏；长日志只摘关键行。

### Merge Danger

说明这是单向门还是双向门。双向门可以走回头路，单向门不行：回滚便宜的 PR 风险低；涉及破坏性操作或难以撤销的决定，就是单向门。

影响面（blast radius）是这次改动可能波及的范围，把能想到的都想一遍：布局跑偏、给调用方带来的破坏、手机端的响应式等。能回滚就写怎么回滚，需要时写兼容风险。
