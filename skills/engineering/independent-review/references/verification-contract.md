# 开发规格中的验收合同

用于 `to-spec` 定义完成标准、`to-tickets` 继承验收项，以及 herdr 审查时判断是否真的交付。小改只填写适用项；不为每个任务强制多 agent、浏览器、完整测试套件或新文档。

## 规格阶段

每项关键用户行为给一个稳定编号（如 A1），写清：

| 验收项 | 前置条件与操作 | 可观察的预期结果 | 验证方式与证据 | 验证责任与完成门槛 |
|---|---|---|---|---|
| A1 | 用户或系统从什么状态做什么 | 应发生什么，什么不能发生 | 已有测试、CLI/API 或实际界面操作；需要保留的输出 | 谁验证，哪些缺口会阻塞交付 |

- 覆盖风险相关的重复操作、失败恢复、取消、并发或引用失效，不机械枚举不适用场景。
- 区分“实现者检查”“独立代码审查”“用户路径验收”。测试全绿或审查通过不能代替 spec 要求的用户路径；截图只能证明可见画面，不能单独证明交互、持久化或后端副作用。
- UI 任务选择能验证所需行为的工具；CLI/API 任务不启动浏览器。Web 交互默认 ego-browser；原生窗口或具体能力缺口按 cua-driver skill 后台操作，不能自动抢焦点。
- 明确是否需要独立审查及其范围。仅在用户明确要求时安排不同关注面的审查者；小改可以只用已有验证。外部 CLI 默认由 herdr 派发，原生 subagent 仅按用户明确选择使用，当前主控负责判断与集成，不引入第二套调度器。
- 规格没有当前实现版本时，把 base/target、运行入口、数据前提和证据位置列为交付时填写项，不能编造已通过的检查。实际路径与命令以项目入口为准。

## 固定审查输入

沿用 [工作目录与交付证据](../../../planning/project-flow/references/delivery.md)。记录 base commit、目标 commit 或未提交快照及实际运行版本；PR 差异以固定的 merge-base 到目标为准，不能把后来变化的主分支顶端当作原基线。

审查者独立完成首轮，不提前互相看报告；只读源码与证据。每项发现包含稳定编号、严重度、触发条件、实际/预期行为、位置、复现或推理证据，以及建议如何验证。关注断言能否抓到错误，不能只读测试名称。

## 逐项处理发现

在现有工单或回执中维护简短表格，不另建数据库：

| 发现编号 | 目标版本 | 判断及依据 | 修复版本 | 验证证据 | 当前状态 |
|---|---|---|---|---|---|
| F1 | SHA/快照 | 复现或反证 | SHA/快照或未修 | 命令、退出码、观察结果 | 待核实 / 已确认未修 / 已修复 / 不成立 / 暂缓 |

- 先验证问题是否存在，再决定修法；问题成立不等于建议修法正确。未复现且证据不足时保留待核实，不能直接记“不成立”。
- 对可执行的行为缺陷，优先证明同一检查在修复前失败、修复后通过。必要时在隔离副本重现旧行为，不在共享工作区或生产撤销修复；确保失败原因确实是目标行为，编译失败、工具缺失、超时都不能冒充回归证据。
- 纯文字、视觉偏好等不能合理红绿测试的改动，记录适用的对照或实际观察；明确缺口，不制造装饰性测试。
- 查询无结果时先确认查询成功；需要时使用已知有结果的对照。零结果、空回执、配额错误和 agent 退出异常均不能当作通过。
- 删除、重复或未接入的判断必须追到实际加载入口、调用链或运行版本；文件名相似、静态搜索无结果和多位审查者同意都不能单独作为证据。先尝试用真实调用反驳发现，再决定修复；被推翻的发现保留更正理由。
- 不成立要有反证或边界依据；暂缓写明原因、风险和后续工单。当前交付新增或加重的阻塞问题不能通过标记“范围外”消失。

## 复查与停止

修复由原执行者或明确指定的单一写入者完成。主控把每位审查者自己的发现、处理依据和新版本发回对应 pane；保留已解决项的理由，避免重复争论。首轮的独立性不能被互相转发意见或“其他人都通过了”替代；新证据可以重新打开旧结论。

按变化重跑受影响检查。所有必需结论必须能关联最终交付版本；变更触及审查范围时需要增量复查，不能直接继承旧 SHA 的通过。未受影响的已有证据可复用，但应说明适用范围。

spec 明确适用的审查轮次或成本边界，并遵守回执与修复次数规则；上限用完时保留未解决项，不以继续空转或降低标准来结束。认证、环境或证据缺失报告阻塞。只有会改变产品选择或任务边界、且现有证据无法裁决的分歧才交用户决定。

交付时分别报告：验收项是否满足、审查发现是否处理、运行证据覆盖到哪里。审查者一致只说明本轮未发现剩余问题，不证明软件无缺陷。规则描述本身不是机器门禁；只有项目实际执行并记录的检查才算验证。

设计参考：[CodeJury](https://github.com/agentsdance/codejury/tree/61b2b33772249523d56e4075ef66e58dc335e878) 的独立审查、逐项判断和版本证据思路。这里按现有 herdr 工作流调整：不安装 Jury 调度器，不照搬自动推送、固定十轮或每次全量测试。
