# herdr 独立审查

先加载本工作站的 `herdr-team` skill，按其派发和验收规则执行。用户要求的外部 CLI 审查者使用 herdr 里的真实 pane；原生 subagent 仅按用户明确选择使用。禁止私有 Worker 池或自动修复循环。

默认的审查者是两位：Claude Opus 5.5（medium）和 GPT Sol 6.1（high），各自独立首轮，需要时再互相核对对方的发现。判定标准、证据规则和“CI 全绿之后还要查什么”见 delivery-verify skill 里的 adversarial-checks 文档。在 Pi 里，`/butler-review` 是同一套标准的内置版本：两个模型直接审当前改动并互相核对，结果生成 delivery-verify 的 HTML 验收报告登记到交付看板；其他宿主走下面的 herdr 真实 pane。

主控按 [工作目录与交付证据](../../planning/project-flow/references/delivery.md) 固定审查输入。给审查者明确只读范围、基线/目标 commit 或内容快照、相关需求与执行过的检查；不要把作者结论当成事实，审查结论不能自动适用于后续改动。

项目采用 spec 验收合同或需要多轮处理发现时，读取 [验收合同](references/verification-contract.md)。按稳定发现编号记录复现、反证、修复及复查；各审查者独立首轮，主控分别回应，结论关联实际交付版本。

审查者独立检查实际代码与行为，寻找可复现的正确性、数据损坏、兼容性或用户可见问题；禁止改文件、提交或推送。必要的测试只能在授权范围内运行。不因个人风格偏好或猜测阻塞。

回执给出以下之一：

- PASS：未发现阻塞问题，并列出审查范围、验证证据和未覆盖部分。
- FAIL：逐项说明严重度、触发条件、实际与预期行为、文件位置或命令证据、如何验证修复。
- BLOCKED：缺少什么证据或环境，不能据此声称通过。

主控读取真实回执并核对证据。确认的问题交给原执行者修复；修复后明确增量范围，再按需续派审查。低风险建议单列，不能把一轮命令成功视为需求已满足，也不能因为多轮未通过而降低标准。存在分歧时回到需求与复现证据，需要裁决再引入独立 pane，不设置隐藏仲裁器。

结果和未解决问题回到当前会话与项目指定 tracker。涉及白板决策时按 `project-flow` 回写 Agora；不要为审查另建任务数据库。
